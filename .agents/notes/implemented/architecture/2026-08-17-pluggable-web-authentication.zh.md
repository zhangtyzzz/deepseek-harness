# Agent Note: Web 认证是一个能力 seam，由载体叠加在其权威栅栏之上

Status: implemented

[English](2026-08-17-pluggable-web-authentication.md) | 中文

## 问题

GUI 宿主以明文 HTTP 提供 `/api`，其背后只有一道[载体级浏览器信任边界](2026-07-28-api-browser-trust-boundary.md)，那是一道混淆代理人防御，并且刻意不是认证。因此，一个必须能从另一台机器访问的部署 —— 隧道后的容器、局域网地址、VPN 对端 —— 在产品内部没有任何东西要求远端调用方证明身份。`dsh web --host 0.0.0.0` 会让 CLI 把本机的局域网 IP 字面量派生进 `trustedHosts`，以便它公布的 URL 可用；这意味着该网络上的每个客户端都能触达 `session.prompt`：一个会运行 bash 的 agent。`PRIVILEGED_METHODS` 集合被钉在回环上，正是因为 `trustedHosts` 不是认证，所以一个正当的远程操作者同样完全触达不到配置面。

部署方以两种方式在产品之外堵这个洞。一种是改写已安装产物的信任检查，让栅栏接受任意 `Host`，那是靠给已发布文件打补丁来关掉一项安全检查，并且每次升级都会失效。另一种是把 harness 留在回环上，前面套一个自己持有登录的网关；这让 harness 无法表达自己的要求，让每套部署各自重新实现一遍登录，并且仍然让钉在回环上的方法无法触达，因为网关的流量不是回环。

传输与凭证证明各自独立变化：同一个操作者可能今天用 Cloudflare Tunnel、明天用 Tailscale、或者只用一个局域网反向代理挡在 harness 前面，而证明身份的方式可能是一个口令、隧道签发的断言，或别的东西。把其中任一选择固化进另一个之中的设计，对这个产品是错的 —— 这里其他每一项能力都是一行可挂载的配置。

## 决策

认证是一个能力 seam，配两个 Provider 包，而这项要求由已经持有浏览器权威栅栏的那个插件来施加。

`@deepseek-ai/dsh-host-web-auth` 提供 `ctx.webAuth`：Provider 注册表、登录会话生命周期，以及会话 Cookie 的编码。它不注册任何路由，也不认识任何传输形态。一个 Provider 至少提供两种校验面之一 —— `verifyRequest` 校验请求自身已携带的凭证，`verifySecret` 校验提交到登录端点的口令 —— 注册表拒绝两者都不提供的 Provider，因为这样一行配置会让认证变为必需，却永远无法放行任何人。校验先以一次 map 查找认可仍然有效的登录会话，再依次运行每个请求凭证 Provider 直到有一个通过；因此注册顺序不承载任何含义，而只支持交互登录的 Provider 不带来任何逐请求开销。

要求跟随 Provider，而非跟随 seam 那一行：`required` 就是 `providers.size > 0`。只挂载 seam 不改变任何行为，而卸载一个 Provider fiber 会连带撤销这项要求。

`@deepseek-ai/dsh-client-connection` 是 Consumer。[`src/api-request-gate.ts`](../../../../packages/client/connection/src/api-request-gate.ts) 为两种权限合并这两项判定，并且逐请求通过 `ctx.get('webAuth')` 读取 seam，因此挂载顺序无关：

- 一个普通 `/api` 请求先通过权威栅栏；在挂载了 Provider 时，它还必须来自回环或携带一个已校验的主体。
- 一个 `loopback` 权限的请求 —— 配置面、原生对话框，以及 `PRIVILEGED_METHODS` 集合 —— 从回环通过，或者从一个已声明的权限携带已校验主体通过。认证正是那道钉子在等的条件，所以完成登录的远程操作者触达的面与本地操作者相同。
- 回环无需凭证仍然触达一切。能访问回环本身就意味着能以 harness 进程的身份运行代码，所以在那里加口令什么也保护不了，却会破坏健康检查与本地工具。
- 凭证在任一权限下都不能替代 `Host` 检查。

登录界面是 `/auth` 下的四条路由 —— 页面、登录、登出、状态 —— 通过 `ctx.inject(['webAuth'], …)` 挂载，并置于同一道权威栅栏之后，因此被重绑定的页面无法把登录端点当作口令预言机使用。有副作用的路由要求 `application/json` 请求体，这迫使任何跨站尝试进入这台服务器从不回答的预检。静态资源不受管：这项要求覆盖 `/api`，与栅栏自身的范围一致。

会话是 256 位随机令牌的 SHA-256 摘要，保存在进程内存中，因此内存泄露得不到可用的 Cookie，而登出是真正的撤销。它们刻意不落盘，这是不在磁盘上持有签名密钥所换来的代价：重启 harness 会使每个浏览器会话失效。每个签发的 Cookie 都带 `HttpOnly`、`SameSite=Strict`、`Path=/`，以及与服务端记录一致的 `Max-Age`。`SameSite=Strict` 正是让一个已认证请求可以安全放行的原因：跨站上下文 —— 包括被 DNS 重绑定的页面 —— 根本不会附上这个 Cookie，所以持有它证明的是第一方上下文，而不只是一个可达的套接字。是否设置 `Secure` 是部署事实而非进程能观察到的事实，因为即使浏览器是经隧道以 HTTPS 抵达，harness 提供的仍是明文 HTTP；`cookieSecure` 在 `auto`、`always`、`never` 之间选择。

随之交付两个 Provider，覆盖交互与委托两种情形：

- `@deepseek-ai/dsh-host-web-auth-password` 在首次启动时从一个 32 符号字母表生成 25 个符号 —— 125 位 —— 打印一次，并只持久化其 scrypt 校验值。凭证文件以独占创建和仅属主权限写入，因此两个在全新 home 目录上同时启动的进程会收敛到同一份凭证而不是互相覆盖，而失败的一方读取胜出者的文件，不会让自己已经打印出去的口令失效。连续失败会把一个客户端锁定一段可配置的时间，而锁定过期后计数重新开始，因此阈值始终描述的是连续失败次数。
- `@deepseek-ai/dsh-host-web-auth-cloudflare-access` 校验 Cloudflare Access 在每个被代理请求上转发的 RS256 应用令牌。`alg` 是钉死的而非从令牌里读取，`iss` 必须等于团队域源，`aud` 必须包含配置的应用标识，因此为同一团队下另一个应用签发的令牌到不了这个 harness。团队的密钥集带 TTL 缓存，未知的 `kid` 在每个冷却窗口内最多触发一次重新拉取，而每一种失败 —— 令牌畸形、拉取出错、密钥集为空 —— 都通过 logger 上报并按未认证请求处理，绝不变成调用方可以当预言机用的 500。

## 曾考虑的替代方案

- **给权威栅栏打补丁使其接受任意 `Host`。** 否决：这对每个采用它的部署都删掉了 DNS 重绑定防御，它是靠编辑已安装产物而非靠配置来实施的，而且它并没有认证任何人 —— 它只是移走了那个让缺失的认证暴露出来的检查。
- **在 harness 前面放一个外部网关，产品内不加任何东西。** 否决：harness 无法表达自己的要求，于是一套组合离一个配错的代理只有一步之遥就变成无认证的 agent；钉在回环上的特权方法对远程操作者仍然不可达，因为网关流量不是回环；而且每套部署都要重新实现一遍登录。在这个 seam 之前放网关仍然完全受支持 —— 它是传输，不是凭证证明。
- **用 Bearer 令牌或 API key 头替代 Cookie 会话。** 作为主机制被否决：客户端是浏览器，而只用头的方案迫使令牌进入脚本可读的存储，失去 `HttpOnly` 以及那条让放行得以安全的 `SameSite=Strict` 性质。Provider 仍然可以认证一个头部凭证 —— `verifyRequest` 就是这个，Cloudflare Access Provider 用的也是它。
- **在 `dsh-host-apiproxy` 里紧挨媒体类型栅栏施加认证，或放在 webserver 里。** 否决：权威栅栏正是这项判定要与之合并的那一个，而它位于 `dsh-client-connection`。把两者拆到不同包会让其中一个放行而另一个拒绝，而 webserver 拥有的是可达性，那是另一项策略。
- **持久化会话以便重启后仍然有效。** 否决：那需要一个签名密钥或一份落盘的会话存储，而当前选择的代价只是重启后重新登录一次。
- **用一个带模式开关的认证插件替代 seam。** 否决：模式枚举会在一个包内为每种机制长出一个分支，无法同时表达两种机制 —— 日常用隧道断言、直连局域网时用口令 —— 并且让第三方机制变成一次 fork 而不是一行配置。
- **把 `trustedHosts` 当作授权名单。** 否决：它规定的是浏览器可以声称哪些权限，那是一道重绑定防御；每个能触达已声明权限的客户端都满足它，所以它无法区分操作者。

## 测试

`packages/client/connection/tests/api-request-gate.host.spec.ts` 钉住合并后的判定，包括：没有 Provider 的组合等价于完全没有 seam 的组合；完美的凭证在两种权限下仍然过不了未声明的 `Host`；以及钉在回环上的那个面向已校验主体开放。`packages/client/connection/tests/auth-routes.host.spec.ts` 用真实 seam 与真实口令 Provider 驱动一台已绑定的 HTTP 服务器，走完登录、锁定、登出，以及媒体类型与请求体大小限制，并断言无 Provider 的组合对 `/auth/login` 回答 404。Provider 测试只用本地夹具：为 Cloudflare Access 生成的 RSA 密钥对与一台本地 JWKS 服务器，以及为口令 Provider 准备的临时 home 目录 —— 其中包含一次四路并发的首次启动。

## 后果

- 一套部署用一个 patch 层加上 seam 那一行与一个 Provider 那一行即可启用认证，因此挡在 harness 前面的传输与 harness 内部的凭证证明是各自独立选择的。
- 没有 Provider 那一行的组合在每条路径上都不受影响，包括 `/auth` 路由并不存在。默认 `web` profile 与纯回环用法的行为与 seam 存在之前完全一致。
- 远程操作者一旦完成认证就能触达配置面与原生对话框路由，这是对非回环客户端能力范围的有意扩大，也是栅栏的 `Host` 要求被保留而非放宽的原因。
- 重启 harness 会让每个浏览器登出，而丢失的口令通过删除凭证文件来恢复 —— 下次启动即轮换。
- Cloudflare Access Provider 通过网络信任团队的密钥集，因此密钥集不可用时，携带头部凭证的调用方降级为未认证；挂载一个口令 Provider 可以让登录在那段窗口内保持可用。
